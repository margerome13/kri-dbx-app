What's changed since the last guide

  • The app itself was renamed from "KRI Intake" to Maya KRI, and now shows the Maya logo in the sidebar.
  • Monthly Intake no longer asks you to pick a RAG status. It's computed automatically from the Actual value against the KRI's thresholds and shown read-only — see "How RAG is decided" below.
  • Add a KRI / Manage Existing KRIs now reject Green/Amber/Red thresholds that overlap or aren't in order, and warn (without blocking) when two thresholds leave an unexplained gap between them.
  • User Role Manager is a new Administration page (this guide's section 6) — it didn't exist in the previous version.
  • User emails in User Role Manager must now match Maya's own account format, firstname.lastname@paymaya.com.

How RAG is decided

The pages

1

Monthly Intake — Submit / Edit Monthly KRI

ADMINMAKERCHECKER

Where departments log their numbers each month.

  1. Pick your Entity → Department → KRI
  2. See that KRI's Green/Amber/Red thresholds displayed for reference
  3. Choose the reporting month
  4. Enter the Actual value — the app shows a live hint for the expected format (e.g. a percentage needs a %, a ratio needs up to 3 decimal places)
  5. RAG status now shows itself as you type, read-only — the app works out Green/Amber/Red from the Actual value against the thresholds above (see "How RAG is decided"). A manual Green/Amber/Red choice only reappears if it genuinely can't be computed — a narrative KRI, or a KRI whose thresholds aren't fully filled in yet
  6. Add remarks (cause, action items, target date) — required whenever the status is Amber or Red
  7. Save. If a submission already exists for that KRI and month, saving updates it instead of creating a duplicate

Dashboard — KRI Overview

ADMIN

A read-only snapshot across all submitted KRIs.

  • Filter by entity, how far back to look, and RAG status
  • See counts of Green/Amber/Red at a glance
  • A table of every KRI's latest status
  • Pick one KRI to see its trend over time (a chart for numeric KRIs, a list of statuses for narrative ones)
  • Expand to see the remarks logged for any Amber/Red month
3

Add a KRI

ADMIN

Where new KRIs get defined before departments can report on them: entity, department, risk category, title, description, monitoring frequency, unit of measure, data source, and the Green/Amber/Red thresholds.

  • Checks that nothing's missing, the title has no special characters, and each threshold matches the selected unit of measure
  • Checks the three thresholds together: Green, Amber, and Red must be sequential and non-overlapping — see "Data validations" below for the exact rule
  • Warns (without blocking) if two thresholds leave a numeric gap wide enough that a real value would match no color
4

Manage Existing KRIs

ADMINCHECKER

Where existing KRIs get reviewed and adjusted.

  • Browse and filter by entity, then pick one
  • Update its thresholds or its status (Active / Inactive / Retired)
  • The same threshold format, sequencing, and gap-warning checks from Add a KRI apply here too

Lookup Values

ADMIN

Where the standardized dropdown options live — entity, department, risk category, frequency, unit of measure, and the various status lists.

  • Add a new option
  • Rename an existing one — a department name change, for example, automatically updates every KRI already using the old name
  • Deactivate one that's no longer needed

User Role Manager — new

ADMIN

Controls who can use the app at all, and what they can see. Changes here take effect immediately — no code change or redeploy needed.

  • Add / update a user — enter their Maya email (firstname.lastname@paymaya.com) and pick ADMIN, MAKER, or CHECKER
  • Remove a user — select them from the current list and remove their access
  • A short hardcoded list always has ADMIN access no matter what's in this table, so the team can never be fully locked out; day to day, the app also refuses to remove or demote the last remaining ADMIN row — add a replacement ADMIN first

A few things that work the same everywhere

  • Nothing you type gets lost. If a form comes back with a validation error, your entries stay exactly as you left them — nothing clears until you save successfully.
  • Error and success messages show twice — once at the top of the form and once at the bottom — so you'll see them whether you're at the top of a long form or already scrolled down to the Save button.
  • Forms that add something new blank themselves out after a successful save, ready for the next entry.

Data validations in place

Plain-language rundown of what the app checks before letting you save. Everything below blocks saving unless it's tagged warns only.

Add a KRI

Nothing can be left blank — every field is required. Miss one, and the app tells you exactly which.

KRI title: letters, numbers, and spaces only — no special characters (no /, -, %, etc.).

Thresholds match the unit of measure — see the format table below.

A threshold written as a range or comparison (e.g. >=75%-90%) needs its lower number genuinely lower than the higher one. 90%-89% is rejected — 90 isn't lower than 89, so that's an invalid range, not a typo the app should silently accept.

Green, Amber, and Red must be sequential and non-overlapping — either increasing (Green < Amber < Red, e.g. 1-3 / 4-6 / 7-10) or decreasing (Red < Amber < Green). 1-5 / 4-6 / 7-10 is rejected because Green and Amber overlap on 4–5.

If two thresholds leave an unexplained numeric gap (e.g. Amber ends at 4 and Red jumps straight to 46), you'll get a heads-up after saving. It still saves — the gap might be deliberate, pending a policy decision — but it's worth a second look.

warns only
Manage Existing KRIs

Every threshold format, sequencing, and gap-warning rule above applies the same way when you edit a KRI's thresholds.

Monthly Intake

Actual value is required — can't save a blank submission.

Actual value must match the KRI's unit of measure — same format table as Add a KRI, so a Percent KRI needs 5%, not just 5.

Unlike a threshold, the Actual value can't be a range or use >/< — you're reporting one number for the month, not a band. >=75% or 75%-90% are rejected here even though they're valid threshold text.

RAG status is computed, not chosen — see "How RAG is decided" above. There's no longer a way to save a value alongside a RAG status that disagrees with it.

Remarks are required whenever RAG status is Amber or Red — you can't flag something as at-risk without explaining why.

Lookup Values

Can't add a value that already exists in that category (e.g. you can't add "Finance" as a department twice).

The ID is assigned automatically and can never be typed or edited — it just quietly keeps each value's identity stable even if its name changes later.

User Role Manager — new

User email must be a real Maya account pattern: firstname.lastname@paymaya.com (e.g. mar.abana@paymaya.com). A different domain, a missing dot, or a middle name/initial all get rejected.

The last remaining ADMIN in the table can't be removed or demoted to another role — add a replacement ADMIN first.
