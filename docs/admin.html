Admin

You run the KRI program: definitions, oversight, access, and corrections. You see all departments unless noted otherwise.

What you see in the app

  • Submit KRI — submit or correct Approved submissions (Makers cannot edit Approved rows).
  • Review — Program queue (all departments), pending review, your own approval/rejection history.
  • Dashboard — KRI Overview, framework signals (trending Amber, persistent Red, missing submissions, etc.).
  • Administration — Add a KRI, Manage Existing KRIs, Lookup Values, User Role Manager.

Onboarding a new user (two steps)

  1. Databricks: On the Maya KRI app, use Share → Can Use for their workspace account.
  2. App role: User Role Manager — pick their email (from the Databricks group list), role, and for Maker/Checker a Department.

App access alone is not enough; User Role Manager alone is not enough — both are required.

Setting up KRIs and departments

  1. Lookup Values — add standardized names (departments, entities, risk categories, etc.).
  2. Add a KRI — define each KRI for an Entity + Department pair (thresholds, frequency, unit).
  3. Until a KRI exists in the catalog for that pair, Makers cannot submit for that department on Submit KRI (lookup alone is not enough).

Running the review workflow

  • Program queue (Review tab) — filter all submissions; act on Submitted items like a Checker when needed.
  • Dashboard → Open program queue — shortcut when you see pending approval counts.
  • Framework alerts (trending Amber, missing submissions, etc.) use Approved data by default — see the checkbox on the dashboard.

Corrections after approval

Makers cannot edit Approved submissions. As Admin, use Submit KRI, open the KRI and period, edit, and save — status stays Approved.

Do’s

  • Keep Lookup Values and catalog definitions aligned (same department spelling everywhere).
  • Assign every Maker and Checker a department in User Role Manager.
  • Use Manage Existing KRIs for threshold/status updates; use Add a KRI for new definitions.
  • Monitor Dashboard signals and the submission workflow block for operational follow-up.

Don’ts

  • Don’t add a department in Lookup Values only and expect Submit KRI to work — add catalog KRIs too.
  • Don’t remove the last Admin in User Role Manager without another Admin in place.
  • Don’t assume Checkers manage the catalog — Checker role is review-only.

If something’s wrong

  • User email not in picklist — they must be a direct member in the Databricks group directory the app reads.
  • Threshold validation errors — see technical reference for unit formats.
  • Maker sees wrong department — update their row in User Role Manager.
